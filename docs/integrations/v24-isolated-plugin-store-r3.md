# Physical quarantine installation lifecycle

`planIsolatedPluginInstall` and `reopenIsolatedPluginInstall` in npm export `/isolated-plugin-store` implement an actual isolated file-tree lifecycle. The store copies verified package files, including `.js` and nested assets, into a new private quarantine root. It never imports/loads those files, accepts an existing destination, modifies DSH or grants activation. Signed receipts retain their review/synthetic staging scope; this is not permission for a production installation or redistribution.

Trusted host composition supplies a Core capability input (with bounded scoped readers), an independent scoped reviewer, its receipts, operator and session. It can plan `install`, `update` or `disable`, then call `store.apply(provider)` and separately `store.rollback(provider)`. `store.inspect()` returns selected metadata, dependencies and current trust; `store.readInstalled(relativePath)` reads only an exact declared selected file. It refuses disabled or currently untrusted packages. No CLI/MCP/Workbench writer or public approval endpoint is added.

Each transaction has its own fresh Core lab. Original/candidate file trees are staged before approval but remain unavailable through the installed-file API. Core approves the sealed transaction-root selector change once; `INSTALLED_QUARANTINED` selects the corresponding exact file tree, while `DISABLED` prevents installed-file lookup. An update copies a verified previous version into the new root, validates the complete candidate and dependency closure, rejects downgrade/no-op/source or package-set changes, and preserves disabled state. This is a bounded whole-closure version update, not a network resolver/updater.

The store seals directory/file identities, the complete file list, digests, snapshot metadata and scoped receipts. Reopen validates the Core context, signed records and every physical payload. Content, membership, identity, hardlink or junction drift fails closed. Independent trust is rechecked after a delayed host approval; revocation after planning or during approval blocks selection. This is not an OS identity boundary or production linearization guarantee for revocation racing an already executing commit. Only trusted local host code may configure authority IDs, roots and persistent revocations.

Rollback requests separate Core approval and restores the exact previous selector bytes. Installed-file reads then return the exact retained previous package bytes. Unselected private quarantine snapshots remain as recovery evidence; rollback does not recursively delete data or claim that all staged payloads disappeared. Unknown partial selector bytes remain manual-recovery cases under the configuration recovery policy. Windows directory fsync/power-loss recovery, adversarial concurrent OS-owner races, production service compatibility and actual plugin execution are not established.

Only a finalized COMMITTED/ROLLED_BACK journal can expose selected files or serve as the baseline of another transaction. A known candidate selector left by an injected failure is still unavailable until the transaction is explicitly recovered; matching bytes alone do not count as a completed installation. Corrupt journals refuse store inspection as well as writes.

The physical installation remains quarantined: `activationAuthorized=false`, `executionAllowed=false`, `productionInstallation=false`. A real DSH install, sandboxed loader, OS-authenticated UI, production trust persistence and rights clearance remain separate unimplemented/unverified work. Tests use only self-authored inert packages and ephemeral in-memory signing keys. The prior encoded `planSyntheticPluginUpdate` API remains compatible and narrower in scope.

`tests/plugin-store-r3.test.mjs` exercises physical files and nested assets, dependency ordering, install/update/disable/read/refusal/restore, separate approvals, post-selector failure/reopen, revocation, session mismatch, unlisted/path/destination refusal, drift/links, downgrade and changed bytes without version advance. None of these tests prove full upstream host-patching equivalence.
