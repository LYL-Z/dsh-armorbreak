# Trusted Gate F-03-R candidate (not deployed)

The external controller is a deployment candidate, not an installed GitHub App. It executes no candidate code or artifact. PR35 remains a four-file worker candidate; its seven common jobs (Node22/24 × Ubuntu/Windows with typecheck, L0 and digest-pinned real Docker L1, aggregate) are independently checked through GitHub API metadata and a pinned control tree.

## R1: candidate binding

Every evaluation binds PR number, head/base repositories (name and numeric ID), head/base refs and SHAs, workflow ID/path/repository, run attempt and its GitHub-owned pull_requests association. Missing/ambiguous/conflicting association is refused. A shared HEAD in another PR/base cannot silently borrow the run. HEAD/base/target/run-attempt are reread immediately before completing a Check.

## R2: merge target

GitHub may evaluate checks on its test-merge commit when that commit has check results. Publish only on the current PR merge_commit_sha, after checking exact ordered base/head parents. This reviewed worker tests HEAD: its evidence qualifies the merge only when the HEAD and merge Git tree OIDs are identical. Different merge content, missing/conflicting merge, base movement or target change refuses publication; a separately reviewed merge-testing worker is then necessary. A PR37 success run is not PR31 acceptance. Retain strict synchronization. Real App enforcement and the GitHub merge box remain UNVERIFIED until separate authorization; do not treat API replay as that proof.

## R3: independent deployment roots

Production entry is `node tools/trusted-gate/bootstrap.mjs PR_NUMBER RUN_ID --dry-run` (or separately authorized --publish). Arbitrary policy path CLI arguments are rejected. Only the owner-controlled service environment sets ARMORBREAK_TRUST_ROOT, a separate read-only mount unavailable to candidate code. It holds signer.pem (offline policy-approval public key), approval.json plus detached Ed25519 approval.sig, minimum-version.json and the approved policy file. Startup verifies the signature, exact policy bytes SHA-256, policy version/minimum, trustCommit binding, controller version and actual byte hashes of all six controller modules before importing the execution controller. Approval records require ID, date and reason. Policy trustCommit is provenance, not identity by itself.

The service launcher/immutable image must independently pin this release and the external root/public key before launching bootstrap. Code cannot establish its own integrity against a host owner who replaces both verifier and root. No production trust root/signer is created by this PR. Test-only generated keys/root manifests are not owner approval or App credentials. Anti-rollback minimum is owner-managed external state. Policy upgrade requires separate review/signing, recorded before/after digests and reason, and controlled invalidation/re-evaluation of previous success checks; never auto-promote PR code or main.

## R4: issuance and failure behavior

Publish mode uses an App JWT from app-private-key.pem in the protected external root, verifies GET /app and installation ID/account/permissions before requesting a short-lived token restricted to one repository. Token response permissions/repository/expiry and token-accessible repositories are verified. No contents/admin write permission is requested. App key never resides in Actions secrets/runner, caches, candidate checkout or logs. Read-only replay uses ARMORBREAK_CONTROLLER_READ_TOKEN and cannot publish.

Check creation is in_progress first; verify issuer/name/SHA/external_id before completion, reread live candidate/base/merge/run attempt, then complete and validate readback. Key external_id includes PR/head/base/ref/merge/policy/controller/run attempt. An owner-protected writable ARMORBREAK_CONTROLLER_STATE directory separate from the read-only root provides an exclusive lease; duplicate deliveries reuse an API receipt. Ambiguous receipts or surviving lease require controlled recovery, never automatic success. Network/timeout/redirect/API/JSON/pagination failures refuse a success decision. An uncertain POST/PATCH is not blindly retried; recover by API receipt + fresh evaluation. If readback is inconsistent, retain logs and treat it as an incident; actual already-published check reconciliation requires production acceptance.

Preferred trigger: external controlled polling with authoritative API refresh on every attempt, serialized updates and periodic resync. No production scheduler/webhook is deployed. Webhook option needs HMAC verification, installation/repository allowlist and durable delivery deduplication; no unauthenticated event data may choose policy/token/target. A PR retarget/base push/synchronize event must promptly supersede prior receipts; checks are commit-scoped on GitHub, so same-SHA cross-PR/base-ref collisions require deployment tests and active invalidation, not a claim of native per-PR check isolation. A stopped service may leave an old result; strict synchronization plus merge-target binding handles changed commit content, while service health/revalidation and explicit incident response remain necessary.
